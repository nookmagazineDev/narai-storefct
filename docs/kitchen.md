# เมนูครัวกลาง

หกหน้าใต้เมนู **ครัวกลาง (Kitchen)** ในแอป storefct

| หน้า | path | ทำอะไร |
|---|---|---|
| สั่งผลิต | `/kitchen/produce` | เลือกเมนู QC/RD → ดูสูตร BOM → กรอกยอดใช้จริงและจำนวนที่ได้ → บันทึกครั้งเดียว |
| รายการสั่งผลิต | `/kitchen/orders` | สองแท็บ: **รายการที่สาขาเบิก** (ของที่ต้องทำ) · **สถานะการผลิต** (คำสั่งผลิต กรองตามสถานะ ค่าเริ่มต้น "ยังไม่เสร็จ") · ตั้งแผนประจำรอบ |
| เบิกวัตถุดิบ | `/kitchen/issue` | บัญชีวัตถุดิบเข้า-ออก: **เบิกออก** ไปใช้ผลิต และ **รับเข้า** เมื่อของมาถึงครัว |
| วัตถุดิบคงเหลือ | `/kitchen/balance` | คงเหลือของครัวกลาง คำนวณสดจากเหตุการณ์ |
| รายการสูตรการผลิต | `/kitchen/recipes` | สินค้าหนึ่งตัวใช้วัตถุดิบอะไรบ้าง ต่อการผลิตหนึ่งครั้ง |
| ดูรายงานการผลิต | `/kitchen/report` | ผลิตอะไรไปเท่าไหร่ เสียเท่าไหร่ ในช่วงที่เลือก |

## ครัวกลางคือ "สาขา" หนึ่งในระบบเดิม

ตัดสินใจไว้ว่าของที่ผลิตเสร็จจะเข้าสต๊อกครัวกลาง แล้วสาขาเบิกผ่านระบบใบเบิกเดิม
ครัวกลางจึงไม่ใช่ระบบแยก แต่เป็นสาขาหนึ่งที่มีรหัสของตัวเอง ผลที่ตามมา:

- **วัตถุดิบและสินค้าที่ผลิต ใช้ `dbo.stock_item` ชุดเดียวกับสาขา** ไม่มี master ซ้อน
  รหัสสินค้าเทียบกันได้ตรงๆ ทั้งระบบด้วย `item_key` ที่ normalize แล้ว
- **ครัวกลางรับวัตถุดิบผ่านใบเบิกเดิม** (`store_fulfillment` / `store_receiving`)
  ไม่มีตาราง "รับวัตถุดิบเข้า" ของครัวกลางเอง เพราะซ้ำกับของที่มีอยู่แล้ว
- **ครัวกลางนับสต๊อกผ่านหน้านับสต๊อกเดิม** ลงที่ `dbo.stock_count` เหมือนทุกสาขา

## สูตรตั้งต้นจากเมนู QC/RD (naraipizzeria)

หน้า **รายการสูตรการผลิต** มีปุ่ม **"ดึงจากเมนู QC/RD"** — เลือกเมนูจากทะเบียนเมนูของ naraipizzeria
แล้วได้ทั้งชื่อเมนูและสูตร (BOM) มาเติมในฟอร์มสูตรของครัว ตรวจแล้วกดบันทึกเหมือนสูตรที่กรอกเอง

- **อ่านจากชีทต้นทุนเมนูเล่มเดียวกับที่ naraipizzeria อ่าน** (`1v8WRT…` แท็บ menu / BOM / item /
  menucodegroup) ผ่าน export CSV ไม่ต้องตั้งกุญแจ ไม่ต้องแก้ฝั่ง naraipizzeria — ตัวอ่านอยู่ที่
  `lib/qcrdMenu.js` แคชไว้ 5 นาที (ปุ่ม "โหลดใหม่จากชีท" ข้ามแคช) ตั้ง `QCRD_SHEET_ID` ทับได้
- **ไม่ได้ก๊อปทั้งทะเบียนมาเก็บ** — เมนูมีหลายพันรายการ ส่วนที่ครัวผลิตจริงมีไม่กี่ตัว
  เลือกทีละเมนู ของที่บันทึกลง `kitchen_recipe` คือสูตรที่ครัวใช้จริงเท่านั้น
- **แปลงหน่วยให้**: QC/RD เก็บยอดใช้เป็นหน่วยเล็ก (กรัม/มล.) แต่ครัวเบิกและคิดคงเหลือเป็นหน่วยสต๊อก
  จึงหารด้วยตัวแปลงหน่วยของชีท (ว่าง = 1000 เหมือนที่ QC/RD คิดต้นทุน) หน้าจอโชว์ทั้งสองตัวเลข
  และเก็บยอดเดิมไว้ในหมายเหตุของแต่ละบรรทัด (`QC/RD 15,000 กรัม`)
- **"ครัวผลิตครั้งละกี่สูตร"** คูณทั้งผลผลิตและวัตถุดิบ — ตารางครัวเก็บทศนิยม 3 ตำแหน่ง ของที่น้อย
  กว่า 0.001 หน่วยสต๊อก (เช่นเกลือ 0.3 กรัมต่อจาน) จะถูกตัดออกและขึ้นเตือน เพิ่มจำนวนสูตรเพื่อให้ติดมา
- รายการที่ติ๊ก **"ไม่ตัด BOM"** ใน QC/RD ถูกข้ามโดยค่าเริ่มต้น (ปิดได้)
- รหัสสินค้าที่ผลิต = รหัสเมนู QC/RD ซึ่งไม่ได้อยู่ใน `stock_item` ถ้ารหัสไปชนวัตถุดิบที่ชื่อไม่ตรงกัน
  ฟอร์มจะเตือน เพราะยอดผลิตจะไปบวกคงเหลือของวัตถุดิบตัวนั้น
- ถ้า naraipizzeria ย้าย QC/RD ไปใช้ SQL (`QCRD_SOURCE=sql`) และเลิกเขียนลงชีท ตัวอ่านนี้ต้อง
  เปลี่ยนไปอ่าน `dbo.qcrd_menu` / `dbo.qcrd_bom` ในฐาน InventoryNarai แทน

## หน้าสั่งผลิต (ผลิตตามสูตร BOM)

เลือกเมนูจาก QC/RD (เฉพาะรหัสของครัวกลาง 10xxxxx / 010xxxx กติกาเดียวกับแผง "รายการที่สาขาสั่งเบิก"
คือ `isKitchenItemCode` ใน `lib/kitchenRequests.js`) แล้วหน้าจอแสดงสูตร BOM คูณตามจำนวนสูตรที่ผลิต มีช่อง **ใช้จริง** ต่อวัตถุดิบ
(กรอกเป็นหน่วยเดียวกับสูตร เช่น กรัม เพราะคนครัวชั่งเป็นหน่วยนั้น) พร้อมผลต่างจากสูตร และช่อง
**จำนวนที่ได้จริง** / ของเสีย กดบันทึกครั้งเดียวได้เอกสารตามลำดับ:

1. คำสั่งผลิต (`saveProductionOrder`) — จำนวนสั่ง = ผลผลิตที่สูตรบอกว่าควรได้
2. ใบเบิกวัตถุดิบผูกกับคำสั่งนั้น (`saveMaterialIssue`) — ยอดใช้จริงแปลงเป็นหน่วยสต๊อก เก็บยอดตามสูตร/ใช้จริงไว้ในหมายเหตุบรรทัด
3. บันทึกผลิตได้ (`saveProductionRun`)
4. ปิดงานเป็น "ผลิตเสร็จ" (ติ๊กไว้เป็นค่าเริ่มต้น — ไม่งั้นได้น้อยกว่าสูตรคำสั่งจะค้างเป็น "กำลังผลิต")

office-server ไม่มี action ที่ทำทั้งหมดใน transaction เดียว หน้าเว็บจึงจำว่าขั้นไหนผ่านแล้ว
ถ้าขั้นหลังพลาด กดบันทึกซ้ำจะทำต่อเฉพาะขั้นที่เหลือ ไม่ออกคำสั่งผลิตหรือใบเบิกซ้ำ
(ถ้าปิดหน้าไปก่อนทำครบ ขั้นที่ผ่านแล้วยังอยู่ ดู/แก้ต่อได้ที่หน้ารายการสั่งผลิตและเบิกวัตถุดิบ)
รายการ "ไม่ตัด BOM" แสดงไว้ให้เห็นแต่ไม่ลงใบเบิก

## คงเหลือคำนวณยังไง

หน้าวัตถุดิบคงเหลือไม่ได้อ่านตัวเลข "คงเหลือ" จากที่ไหน — คำนวณสดทุกครั้ง:

```
คงเหลือ = ยอดนับล่าสุด (stock_count ของสาขาครัวกลาง)
        + รับเข้าหลังวันนับ (kitchen_material_receipt + store_receiving)
        - เบิกไปใช้หลังวันนับ (kitchen_material_issue)
        + ผลิตได้หลังวันนับ (kitchen_production_run)
```

ตัวตั้งคือการนับจริง ไม่ใช่ยอดสะสมตั้งแต่ต้น การนับสต๊อกรอบใหม่จึงล้างความคลาดเคลื่อน
ที่สะสมมาให้เองโดยอัตโนมัติ

เส้นแบ่งคือ *หลังวันที่นับ* ไม่ใช่ *หลังเวลาที่นับ* เพราะใบรับของกับใบเบิกวัตถุดิบเก็บแค่วันที่
ไม่มีเวลา รายการที่เกิดในวันเดียวกับที่นับจึงไม่ถูกรวม — ถูกต้องถ้านับตอนปิดร้าน
และเป็นกติกาเดียวกับที่หน้าสต๊อกสาขาใช้อยู่

สินค้าที่ยังไม่เคยถูกนับที่ครัวกลางเลย จะรวมรับเข้า/เบิกใช้ทั้งหมดตั้งแต่ต้น หน้าเว็บขึ้นคำเตือน
ให้เห็นชัดว่ารายการไหนอยู่ในสภาพนี้

## คำสั่งผลิตมาจากไหน

คอลัมน์ `source` เก็บที่มาไว้เสมอ เพราะเวลาตัวเลขดูแปลก คำถามแรกคือ "ใครสั่ง"

| source | ป้ายในหน้าเว็บ | เกิดจาก |
|---|---|---|
| `manual` | กรอกเอง | ครัวกลางเลือกสินค้าและใส่จำนวนในหน้ารายการ |
| `demand` | ยอดสาขา | รวมยอดที่สาขาสั่งเบิกในหน้านับสต๊อก (ดูหัวข้อถัดไป) |
| `plan` | ตามแผน | สร้างจาก `kitchen_production_plan` (รายวัน/รายสัปดาห์) |

`UNIQUE (produce_date, product_key, source)` กันใบซ้ำ กดปุ่มสร้างซ้ำวันเดิมจึงปลอดภัย:

- **สร้างจากยอดสาขา** อัปเดตจำนวนของใบเดิม (ยอดเบิกยังขยับได้จนกว่าจะปิดรอบ)
- **สร้างจากแผน** ข้ามใบที่มีอยู่แล้ว ไม่ทับ (ครัวอาจแก้จำนวนไปแล้ว)

## รายการที่สาขาสั่งเบิก (หน้ารายการสั่งผลิต)

ด้านบนของหน้ารายการสั่งผลิตแสดงของที่สาขาสั่งเบิก ตามช่วงวันส่งที่เลือก (ค่าเริ่มต้น วันนี้–พรุ่งนี้)
รวมยอดต่อสินค้า กดที่ชื่อเพื่อดูรายสาขา/เลขใบ กด "สั่งผลิต" รายตัว หรือ "สร้างคำสั่งผลิตทั้งหมด"

- **แหล่งข้อมูล:** `myfbdata.orderd` บน MySQL ของ POS ตารางเดียวกับที่ปุ่ม "สั่งของ" ในหน้านับสต๊อก
  ของ Narai-branch เขียน (`api/insert_order.js`, `Ord_ReqType = 'TRF'`) ครัวจึงเห็นยอดตั้งแต่สาขากดส่ง
  ไม่ต้องรอสโตร์ดึงใบไปจัด (เดิมปุ่ม "สร้างจากยอดสาขา" อ่าน `store_fulfillment` ซึ่งมีของหลังสโตร์ดึงใบแล้ว
  และแสดงเฉพาะสินค้าที่มีสูตร — ตอนนี้ใช้แหล่งเดียวกับแผงนี้ ไม่ต้องมีสูตรก่อน)
- **เฉพาะรหัสของครัวกลาง:** เลข 7 หลักขึ้นต้น `10` (เช่น `1000077`) หรือ 7 หลักขึ้นต้น `010`
  รวมแบบที่เติม 0 หน้า `10xxxxx` (`01000077`) ด้วย เพราะบางแหล่งเขียนรหัสเดียวกันแบบนั้น — กติกาอยู่ที่
  `isKitchenItemCode` ใน `lib/kitchenRequests.js`
- **ใบที่ยกเลิก ("ยกใบเบิก") ไม่นับ** — ถ้าโหลดรายการใบยกเลิกไม่ขึ้น แผงจะเตือนว่ายอดอาจรวมใบที่ยกเลิกแล้ว
- หน่วยต่างกันของสินค้าเดียวกันแยกเป็นคนละแถว (บวกกันไม่ได้)
- route: `GET /api/kitchen_branch_requests?from=&to=` ใน `server.js` (ช่วงไม่เกิน 31 วัน)

## เส้นทางข้อมูล

```
เบราว์เซอร์ -> POST /api/kitchen (storefct บน Vercel)
            -> office-server :8787/schedule (เครื่องที่ออฟฟิศ)
            -> SQL Server / InventoryNarai
```

route เดียวส่งต่อทุก action แทนที่จะแยก route ละ action ชื่อ action ถูกกรองด้วย allowlist
ใน `lib/kitchenDb.js` ก่อนเสมอ — สำคัญ เพราะ `/schedule` ของ office-server รวม action
ของทุกระบบไว้ที่เดียว ทั้งตารางงาน พนักงาน และล็อกอิน

| ที่ | ไฟล์ |
|---|---|
| หน้าเว็บ | `src/pages/kitchen/*.jsx` · `src/components/kitchen/ItemPicker.jsx` · `QcrdMenuPicker.jsx` · `QcrdMenuImport.jsx` |
| เมนู/สูตร QC/RD | `lib/qcrdMenu.js` · `server.js` (`/api/qcrd_menus`, `/api/qcrd_recipe`) |
| ตัวเรียก API | `src/services/kitchenService.js` |
| route + allowlist | `server.js` (`/api/kitchen`) · `lib/kitchenDb.js` |
| ตรรกะ SQL | `office-server/kitchen.js` ของ repo **Narai-branch** |
| สคีมา | `docs/schema-kitchen-sqlserver.sql` |

## ขั้นตอนเปิดใช้

1. **รันสคีมา** บนเครื่องที่ออฟฟิศ

   ```
   sqlcmd -S localhost\SQLEXPRESS -d InventoryNarai -U sa -P '<รหัสผ่าน>' -b -i docs\schema-kitchen-sqlserver.sql
   ```

   หรือเปิดใน SSMS แล้วกด Execute — ได้ 7 ตาราง: `kitchen_recipe`, `kitchen_recipe_item`,
   `kitchen_production_plan`, `kitchen_production_order`, `kitchen_production_run`,
   `kitchen_material_issue`, `kitchen_material_receipt`

2. **ตั้งรหัสสาขาของครัวกลาง** ใน `.env` ของ office-server แล้วรีสตาร์ต `NaraiUsageAPI`

   ```
   KITCHEN_BRANCH=<รหัสสาขาครัวกลาง>
   ```

   ตอนนี้ครัวกลางยังไม่ใช่สาขาในระบบ ค่านี้จึงยังไม่มีข้อมูลให้จับคู่ ตั้งเป็น `kitchen` ไว้ก่อนได้
   มันมีผลแค่สองคอลัมน์ในหน้าคงเหลือ คือ "นับล่าสุด" (จาก `stock_count`) กับส่วนของ "รับเข้า"
   ที่มาจาก `store_receiving` — ซึ่งทั้งคู่จะเป็น 0 จนกว่าครัวจะถูกเพิ่มเป็นสาขาจริงและเริ่มนับสต๊อก
   ระหว่างนี้คงเหลือคิดจากใบรับเข้าของครัวเองล้วนๆ ซึ่งถูกต้องอยู่แล้ว

3. **deploy office-server** — `git pull` ที่ `D:\Narai-branch-main` แล้วรีสตาร์ตเซอร์วิส

4. **deploy storefct** บน Vercel (merge เข้า main แล้ว Vercel build ให้เอง)

5. **สร้างสูตรก่อนใช้งานจริง** — หน้าอื่นงอกจากสูตรทั้งหมด:
   ปุ่ม "สร้างจากยอดสาขา" แสดงเฉพาะสินค้าที่มีสูตร · ปุ่ม "คำนวณวัตถุดิบตามสูตร"
   ในหน้าเบิกวัตถุดิบต้องมีสูตร · หน้าวัตถุดิบคงเหลือแสดงเฉพาะของที่อยู่ในสูตรหรือเคยถูกเบิก

## ยังไม่ได้ทำ

- **ไม่มีล็อกอิน** — storefct ทั้งแอปยังไม่มีระบบผู้ใช้ ช่อง "ผู้บันทึก" จึงลงเป็น `ครัวกลาง`
  ทุกครั้ง โครงสร้างรองรับไว้แล้ว (`recorder` รับค่าจาก session ถ้ามี) พอเพิ่มล็อกอินก็ใช้ได้เลย
- **ของที่ผลิตเสร็จยังไม่เข้าสต๊อกอัตโนมัติ** ในแง่ของหน้าสต๊อกสาขา — `kitchen_production_run`
  ถูกนับรวมในหน้าวัตถุดิบคงเหลือของครัวกลางแล้ว แต่ยังไม่ได้เขียนกลับไปที่ `stock_count`
  ซึ่งเป็นตารางของ "การนับ" ไม่ใช่ "ยอดคงเหลือ" การเขียนผลผลิตลงไปจะทำให้ประวัติการนับปนกับ
  สิ่งที่ไม่ได้นับ ถ้าต้องการให้เชื่อมกันจริงควรทำเป็นตารางความเคลื่อนไหวแยก ไม่ใช่ยัดลงตารางนับ
- **ครัวกลางยังไม่ใช่สาขาในระบบ** จึงไม่มีใบเบิกของตัวเอง ไม่ถูกนับรวมในหน้ารวมสต๊อกทุกสาขา
  และนับสต๊อกผ่านแอปสาขาไม่ได้จนกว่าจะมีบัญชีผู้ใช้ที่ผูกกับรหัสครัว ถ้าต้องการให้ครบวงจรจริง
  ต้องเพิ่มครัวเป็น outlet ในระบบ POS (เป็นของผู้ขาย เราเพิ่มเองไม่ได้) แล้วเติมลง `lib/branches.js`
- **ยังไม่มีการเช็คว่าเบิกเกินคงเหลือ** — เบิกได้เลย แล้วหน้าคงเหลือจะโชว์ติดลบเป็นสีแดง
  ตั้งใจให้เป็นแบบนี้ก่อน เพราะยอดคงเหลือช่วงแรกยังไม่แม่นจนกว่าจะนับสต๊อกครบรอบ
  ถ้าบล็อกตั้งแต่ต้นจะกลายเป็นว่าเบิกของจริงไม่ได้เพราะตัวเลขในระบบผิด
