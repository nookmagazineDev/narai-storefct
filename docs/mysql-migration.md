# ย้ายงานสโตร์จาก Google Sheets ไป MySQL

เอกสารนี้คู่กับ [schema-store.sql](schema-store.sql)

## ทำไม

ตอนนี้สถานะการทำงานของโกดัง (จัดของ / รับของ / ดึงข้อมูลใบเบิก / ยกเลิกใบเบิก) เก็บใน
Google Sheet แล้วอ่านกลับผ่าน gviz ซึ่งมีปัญหาสะสมอยู่ 4 ข้อ

1. **ช้า** — ทุกครั้งที่เปิดหน้า ต้องดึงทั้งแท็บมา parse แล้วยุบ "แถวหลังสุดชนะ" ใน memory
2. **ข้อมูลไม่สด** — แคช 15 นาทีสำหรับสถานะรับของ/ดึงข้อมูล/ยกเลิก และ 1 ชั่วโมงสำหรับหมวดหมู่
3. **เขียนแล้วไม่รู้ผล** — การเขียนผ่าน Apps Script ยิงแบบ fire-and-forget ไม่รอคำตอบ
   (`server.js` ใน `/api/save_fulfillment` และ `/api/mark_fetched`) เขียนไม่ติดก็ไม่มีใครรู้
4. **JOIN กับใบเบิกจริงไม่ได้** — ข้อมูลใบเบิกอยู่บน MySQL (`myfbdata.orderd`) คนละที่กัน
   ต้องจับคู่ด้วยเลขที่ใบเบิกในโค้ดเอาเอง

## เลือก MySQL ไม่ใช่ SQL Server

โปรเจกต์พี่น้อง [Narai-branch](https://github.com/nookmagazineDev/Narai-branch) ย้ายหน้านับสต๊อก
ไป **SQL Server** (`InventoryNarai`) แล้ว แต่ต้องเดินผ่านตัวรีเลย์ `office-server` เพราะไฟร์วอลล์
ของ SQL Server ที่ออฟฟิศเปิดให้เฉพาะ IP ในไทย — Vercel ต่อตรงไม่ได้

แอปนี้เลือก **MySQL** ด้วยเหตุผลสามข้อ

- ต่อตรงจาก Vercel ได้อยู่แล้ว (ทุก endpoint ที่อ่าน `orderd`/`item`/`store` ทำงานอยู่ทุกวัน)
  ไม่ต้องตั้งและดูแล office-server เพิ่มอีกตัว
- ข้อมูลที่จะย้ายต้อง JOIN กับ `myfbdata.orderd` เป็นหลัก ซึ่งอยู่บน MySQL — ถ้าไปอยู่คนละ
  เครื่องกับใบเบิก ก็ยังต้องจับคู่ในโค้ดเหมือนเดิม ไม่ได้อะไรขึ้นมา
- เขียนลง MySQL เครื่องนี้ได้จริงและทำอยู่แล้ว: `api/insert_order.js` ของ Narai-branch
  INSERT ลง `myfbdata.orderd` ตรงๆ จาก Vercel

ตารางใหม่อยู่ในฐาน **`narai_store`** แยกจาก `myfbdata` — เหตุผลอยู่ในหัวไฟล์ `schema-store.sql`

## ขอบเขต

| ชุดข้อมูล | ชีทเดิม | ใครเขียน | สถานะ |
|---|---|---|---|
| จัดของ | `จัดของ` | แอปนี้ | **dual-write แล้ว** |
| ดึงข้อมูลใบเบิก | `ดึงข้อมูลใบเบิก` | แอปนี้ | **dual-write แล้ว** |
| รับของ (อนุมัติแก้ไข) | `รับของ` | Narai-branch + แอปนี้ | **dual-write เฉพาะการอนุมัติ** — แถวหลักยังมาจากการซิงก์ |
| ยกเลิกใบเบิก | `ยกเลิกใบเบิก` | ระบบภายนอก | ซิงก์อย่างเดียว |

**ไม่อยู่ในขอบเขต** และตั้งใจไม่แตะ

- **หมวดหมู่สินค้า (Col N)** — ทีมงานกรอกมือในชีท BOM ถ้าย้ายเข้าฐานต้องทำหน้า UI ให้แก้ก่อน
- **ข้อมูลนับสตอค** — Narai-branch ย้ายไป SQL Server `dbo.stock_count` ไปแล้ว
  ⚠️ `/api/stock_count_summary` ของแอปนี้ยังอ่านชีท `ข้อมูลนับสตอค` อยู่ ขณะที่ `saveStock`
  ฝั่งโน้น *"เขียนลง SQL อย่างเดียว ไม่เขียนชีทอีกแล้ว"* (`office-server/stock.js`) แปลว่าหน้า
  "รวมสต๊อกทุกสาขา" น่าจะโชว์ข้อมูลค้างอยู่ — **เรื่องนี้ต้องตามแยกต่างหาก ไม่เกี่ยวกับการย้ายครั้งนี้**

## ระวัง: มีใบเบิกอีกก้อนบน SQL Server ที่ไม่ใช่ตัวเดียวกัน

`dbo.stock_request` (SQL Server `InventoryNarai`) เก็บรายการที่สาขาขอเบิกไว้ด้วย เขียนโดย
`saveStock` ของ Narai-branch ตอนสาขากดบันทึกหน้านับสตอค **อย่าเอามาปนกับ `doc_no` ในเอกสารนี้**

การกดบันทึกหนึ่งครั้งที่หน้านับสตอคเขียนสองที่พร้อมกัน แล้วตั้งเลขคนละแบบ

| | `dbo.stock_request` | `myfbdata.orderd` |
|---|---|---|
| เลขที่ | `CRM2608001` (สาขา+ปี+เดือน+ลำดับ 3 หลัก) | `3451` — หน้าเว็บโชว์เป็น `CRM-3451` |
| ที่มาของเลข | `MAX(doc_no)+1` ในตารางตัวเอง | `config.Cfg_LstOrdID + 1` ของ POS |
| ใช้ที่ไหน | สมุดบันทึกของหน้านับสตอค | **ใบเบิกตัวจริง — แอปนี้และตารางในเอกสารนี้ใช้ตัวนี้** |

ไม่มีคอลัมน์ไหนเก็บความสัมพันธ์ระหว่างสองเลขนี้ จับคู่ได้แค่เดาจากสาขา+วันที่+รายการ

สิ่งเดียวที่มีใน `stock_request` แต่ไม่มีใน `orderd` คือ **`requester` (ชื่อผู้เบิก)** และ
`request_date` — `orderd` ไม่มีที่เก็บชื่อผู้เบิกเลย (`Ord_Rmk1`-`Ord_Rmk10`, `Ord_Remark`,
`Ord_ItmRemark` ถูกเขียนเป็นค่าว่างทั้งหมด) ถ้าวันหนึ่งอยากให้หน้าจัดของโชว์ว่าใครเป็นคนเบิก
ต้องดึงจากก้อนนั้น และต้องแก้เรื่องการจับคู่เลขให้ได้ก่อน

## แผนเป็นเฟส

| เฟส | สิ่งที่ทำ | สถานะ |
|---|---|---|
| 1 | สร้างตาราง + เขียนสองที่ (ชีท + MySQL) + ย้ายข้อมูลเก่า | **เสร็จแล้ว (ยังไม่เปิดสวิตช์)** |
| 2 | เทียบข้อมูลสองฝั่งว่าตรงกัน แล้วสลับฝั่งอ่านมาที่ MySQL | ยังไม่ทำ |
| 3 | เลิกเขียนชีท ถอด Apps Script ออก | ยังไม่ทำ |

เฟส 1 ออกแบบให้ **ย้อนกลับได้ทันที**: ยังไม่มีใครอ่านจาก MySQL เลย และถ้าเขียน MySQL ไม่สำเร็จ
จะแค่ log ไว้ ไม่ทำให้คนกดบันทึกพัง (`bestEffort()` ใน `lib/storeDb.js`) ปิด `STORE_DB_WRITE`
เมื่อไหร่ ระบบกลับไปเหมือนเดิมทุกประการ

## วิธีเปิดใช้งาน

ทั้งหมดนี้ทำกับ **MySQL** เท่านั้น ไม่ต้องไปแตะ SQL Server (`InventoryNarai`) เลย

```bash
# 1. สร้างฐานข้อมูลและตาราง (ครั้งเดียว)
mysql -h inventory.dyndns.tv -u root -p < docs/schema-store.sql

# 2. ย้ายข้อมูลเก่าจากชีทเข้า MySQL (รันซ้ำได้ ไม่เกิดแถวซ้ำ)
node scripts/sync-store-db.mjs

# 3. เทียบจำนวนแถวในฐานกับที่เห็นในชีทจริง
node scripts/sync-store-db.mjs --check
```

รันจากเครื่องไหนก็ได้ที่ต่อ MySQL และเปิดเว็บ Google Sheets ได้ — เครื่องที่ออฟฟิศสะดวกที่สุด
เพราะมี Node.js ติดตั้งอยู่แล้ว (office-server รันอยู่บนนั้น) และอยู่ในเน็ตออฟฟิศ

### ⚠️ ถ้าจำนวนแถวไม่ตรงกับในชีท ต้องรันซ้ำด้วย `--csv`

gviz คืนกลับมา **เฉพาะแถวที่ผ่าน "ตัวกรอง" ที่เปิดค้างไว้ในชีท** โดยไม่ฟ้องอะไรเลย ทีม
Narai-branch เจอของจริงมาแล้วตอนย้ายชีท `ข้อมูลนับสตอค` — gviz ให้มา 6,112 แถว ทั้งที่ของจริง
70,785 แถว (ดู `docs/stock-sql-migration.md` ของโปรเจกต์นั้น)

```bash
node scripts/sync-store-db.mjs --csv
```

โหมดนี้อ่านผ่าน export CSV ซึ่งไม่สนใจตัวกรอง แต่ต้องรู้ gid ของแท็บ — `จัดของ` กับ `รับของ`
รู้อยู่แล้ว ส่วนอีกสองแท็บถูก Apps Script สร้างตอนใช้งานจริงจึงต้องเปิดแท็บนั้นในเบราว์เซอร์
แล้วคัดเลขท้าย URL มาใส่เอง

```bash
node scripts/sync-store-db.mjs --csv --gid-fetched=<เลข> --gid-cancelled=<เลข>
```

การรันซ้ำปลอดภัยเสมอ (UPSERT) รันด้วย `--csv` ทับของที่ย้ายมาด้วย gviz ได้เลย

จากนั้นตั้ง `STORE_DB_WRITE=1`

- **ในเครื่อง**: ใส่ใน `.env`
- **บน Vercel**: Project Settings → Environment Variables แล้ว redeploy

ตอนบูต เซิร์ฟเวอร์จะบอกเองว่าเขียนกี่ที่

```
📝 Dual-write เปิดอยู่ — บันทึกลงทั้ง Google Sheet และ MySQL (narai_store)
```

## ระหว่างที่ยัง dual-write

แท็บ `รับของ` กับ `ยกเลิกใบเบิก` มีระบบอื่นเป็นคนเขียน แอปนี้จึงต้องซิงก์ตามเป็นระยะ ถ้าจะเทียบ
ข้อมูลให้ตรงจริงก่อนสลับฝั่งอ่านในเฟส 2 ให้ตั้ง cron ไว้

```bash
node scripts/sync-store-db.mjs รับของ ยกเลิกใบเบิก
```

ส่วน `จัดของ` กับ `ดึงข้อมูลใบเบิก` ไม่ต้องซิงก์ซ้ำ เพราะแอปนี้เขียนตรงลง MySQL อยู่แล้ว

## สิ่งที่ยังไม่ได้ทดสอบ

โค้ดชุดนี้เขียนในสภาพแวดล้อมที่ต่อ MySQL และ Google Sheets ไม่ได้ ผ่านเฉพาะ

- ตรวจ syntax ทุกไฟล์ (`node --check`)
- unit test ของฟังก์ชันล้วน: normalize รหัส, แยกเลขที่ใบเบิก, แปลงวันที่ทั้ง 4 รูปแบบ
  (รวม พ.ศ. -> ค.ศ.), และพฤติกรรม "เขียนพลาดแล้วไม่ทำให้คำขอพัง"
- ตัวแกะ CSV: หัวตาราง, field ที่มี comma, อัญประกาศซ้อน, เซลล์ที่ข้ามบรรทัด, รหัสแบบ `4501.0`
  และกรณีชีทไม่ได้แชร์แล้วได้ HTML กลับมาแทน

**ยังไม่เคยรันจริง**: คำสั่ง SQL ในไฟล์สคีมา, การ UPSERT, และการซิงก์จากชีท
กรุณารันข้อ 1-3 ข้างบนบนเครื่องที่ต่อฐานได้ แล้วดูผลก่อนเปิด `STORE_DB_WRITE`
